# ADR 0002: HIPAA Architecture

**Status:** Accepted

> Historical status: This ADR records the former AWS reference architecture. It is not the current production operating model as of May 2026. Current hosting and deploy operations use Cloudflare Workers, Cloudflare R2, runtime database configuration for managed PostgreSQL, and Wrangler scripts. Use `docs/runbooks/cloudflare-bootstrap.md`, `docs/runbooks/database-restore.md`, and `docs/runbooks/key-rotation.md` for current operations.

---

## Context

PHIGuard processes Protected Health Information (PHI) on behalf of covered entities (small medical clinics). As a Business Associate, PHIGuard must implement the HIPAA Security Rule's technical, physical, and administrative safeguards. This ADR documents the architectural decisions that implement those safeguards at the infrastructure and application layer.

The full control inventory is maintained in `docs/hipaa/safeguards-map.md`. This ADR focuses on the *architectural* decisions: the ones that constrain all future implementation work.

---

## Decisions

### VPC Layout

**Decision:** 2-AZ VPC with strict subnet separation.

```text
VPC (10.0.0.0/16)
├── AZ-A
│   ├── Public subnet  10.0.0.0/24   (ALB only)
│   └── Private subnet 10.0.2.0/24   (ECS tasks, NAT egress)
├── AZ-B
│   ├── Public subnet  10.0.1.0/24   (ALB only)
│   └── Private subnet 10.0.3.0/24   (ECS tasks, NAT egress)
└── Isolated subnet group (no route table to internet)
    └── RDS Multi-AZ instances
```

**Rules:**
- The ALB is the only resource in a public subnet. It terminates TLS and proxies to ECS tasks in private subnets.
- ECS Fargate tasks run in private subnets. Outbound internet access goes through a NAT Gateway (needed for ECR image pulls, Resend API, Sentry). The NAT Gateway is in the public subnet; tasks never have public IPs.
- RDS lives in isolated subnets with no route to the internet. It is only reachable from ECS task security groups via an explicit inbound rule on port 5432.
- No SSH/bastion hosts. Database access for break-glass scenarios uses AWS Systems Manager Session Manager with IAM-controlled access and full CloudTrail logging.

**Rationale:** Defense-in-depth. Even if an ECS task is compromised, the attacker cannot reach RDS directly from the internet. Even if the ALB is misconfigured, it cannot proxy to the database tier.

### KMS Key Hierarchy

**Decision:** One Customer Managed Key (CMK) per environment. Three data keys derived per CMK.

```text
CMK: phiguard-{env}  (annual automatic rotation enabled)
├── Data key: rds-{env}         (RDS Transparent Data Encryption)
├── Data key: s3-attachments-{env}  (S3 bucket for PHI file attachments)
└── Data key: s3-audit-{env}    (S3 bucket for nightly audit log exports)
```

**Environments:** `dev`, `staging`, `prod`. Each environment has its own CMK so a compromise in dev cannot affect prod data, and key policies can be scoped per-environment.

**Key policies:**
- Only the ECS task IAM role may use the data keys (via `kms:GenerateDataKey` and `kms:Decrypt`).
- The RDS service role uses the RDS data key via the RDS service principal.
- The `kms:CreateKey` and `kms:ScheduleKeyDeletion` permissions are restricted to the break-glass IAM role and require MFA.

**Key rotation:** AWS automatic annual rotation is enabled on all CMKs. Rotation creates a new backing key material but preserves the CMK ARN: existing ciphertext continues to decrypt transparently.

**Rationale:** Separate data keys for separate data stores limit the blast radius of a key compromise. Separate CMKs per environment prevent environment cross-contamination.

### Audit Log Design

**Decision:** Append-only `audit_events` table in Postgres, with nightly export to S3 Object Lock.

#### Table schema (canonical definition in `packages/db/src/schema/audit-events.phi.ts`)

| Column | Type | Notes |
|---|---|---|
| `id` | UUID | Generated by the database (`gen_random_uuid()`) |
| `tenant_id` | UUID | Organization/clinic identifier; foreign key to `organizations` |
| `actor_id` | UUID | User who performed the action; nullable for system actions |
| `action` | VARCHAR(128) | Dot-notation string, e.g. `task.created`, `user.role_changed` |
| `resource_type` | VARCHAR(64) | e.g. `task`, `user`, `attachment` |
| `resource_id` | UUID | PK of the affected resource |
| `before_state` | JSONB | Full resource snapshot before the action; NULL for creates |
| `after_state` | JSONB | Full resource snapshot after the action; NULL for deletes |
| `ip_address` | INET | Client IP from the request; sourced from ALB forwarded-for header |
| `user_agent` | TEXT | Raw User-Agent string |
| `created_at` | TIMESTAMPTZ | Server time at insert; set by `DEFAULT now()` |

#### Immutability enforcement

A Postgres trigger on the `audit_events` table raises an exception on any `UPDATE` or `DELETE` statement, including those issued by superusers through the application's database role. The trigger is defined in the Drizzle migration for the `audit_events` table.

```sql
CREATE OR REPLACE FUNCTION audit_events_immutable()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  RAISE EXCEPTION 'audit_events rows are immutable';
END;
$$;

CREATE TRIGGER audit_events_no_update
  BEFORE UPDATE OR DELETE ON audit_events
  FOR EACH ROW EXECUTE FUNCTION audit_events_immutable();
```

Circumventing this trigger requires DDL access (`DROP TRIGGER`), which the application's database role does not have. DDL changes require the migration IAM role, which is separate and logged via CloudTrail.

#### Nightly S3 export

A scheduled ECS task runs nightly at 02:00 UTC. It:
1. Queries all `audit_events` with `created_at` in the previous calendar day.
2. Serializes to newline-delimited JSON (NDJSON).
3. Uploads to the `s3-audit-{env}` bucket under the key `year={Y}/month={M}/day={D}/audit.ndjson.gz`.

The bucket uses **S3 Object Lock in compliance mode** with a **6-year (2,190-day) retention period**, satisfying HIPAA §164.316(b)(2)(i) which requires documentation retention for 6 years from creation or last effective date.

Object Lock compliance mode means no IAM principal (including the AWS account root) can delete or overwrite objects before the retention period expires.

#### In-app audit viewer

The `apps/web` audit trail UI provides:
- Filtered view scoped to the current tenant (enforced server-side via `tenant_id` predicate)
- Filters by date range, action type, actor, and resource type
- Paginated results (cursor-based, no offset)
- CSV export of filtered results (streamed from the server, not buffered in the browser)
- No raw JSONB display in the UI: `before_state` and `after_state` are rendered as human-readable diffs per resource type

### PHI Handling Conventions

**Decision:** PHI-touching code is identified at the file level, and PHI fields are never passed to external services without explicit scrubbing.

**`.phi.ts` naming convention:**
Any TypeScript file that defines a database table, query, or type containing PHI columns must be named with the `.phi.ts` suffix (e.g., `patients.phi.ts`, `tasks.phi.ts`). This makes PHI scope immediately visible in code review and makes it trivial to grep for all PHI-touching files:

```bash
grep -r "\.phi\.ts" packages/db/src/schema/
```

**PHI field enumeration:**
`docs/hipaa/safeguards-map.md` maintains the authoritative list of tables and columns that contain PHI. This list is reviewed in every security review cycle.

**PHI in logs:**
The application logger exports a `logger.safe()` method. `logger.safe()` accepts the same arguments as `logger.info()` but runs all string arguments and object values through a PHI-scrubbing function before emission. The scrubbing function redacts known PHI field names (e.g., `patientName`, `dob`, `ssn`, `mrn`, `phone`, `email` in PHI context) by replacing their values with `[REDACTED]`. Plain `logger.info()` / `logger.error()` may not be called in `.phi.ts` files. This is enforced by an ESLint custom rule (`no-unsafe-logger-in-phi`).

**PHI in error tracking (Sentry):**
The Sentry `beforeSend` hook in `apps/web` strips:
- All request body content (PHI may appear in POST/PATCH bodies)
- All cookie values
- Any event breadcrumb with `category: "xhr"` or `category: "fetch"` that includes a URL matching PHI-route patterns

This means Sentry receives stack traces, error types, and sanitized context, but never PHI field values.

### Encryption in Transit

**Decision:** TLS 1.2+ enforced at the ALB layer. No HTTP endpoints exist.

- The ALB listener on port 80 redirects to port 443 (HTTP 301). No application traffic traverses plaintext.
- ALB is configured with the `ELBSecurityPolicy-TLS13-1-2-2021-06` policy, which supports TLS 1.2 and TLS 1.3 and disables all older cipher suites.
- The application server sets the `Strict-Transport-Security` header: `max-age=63072000; includeSubDomains; preload`.
- Internal VPC traffic (ALB → ECS) uses HTTP over the private subnet. This is acceptable under HIPAA because the VPC network boundary is trusted and no traffic leaves AWS infrastructure. This may be revisited if inter-service traffic becomes sensitive.

### Breach Notification

**Decision:** HIPAA §164.404 requires notification of affected individuals within 60 days of discovering a breach. PHIGuard's operational response procedure is documented in `docs/runbooks/incident-response.md`.

**Key architectural dependencies for breach response:**
- `audit_events` table provides the authoritative record of which actors accessed which resources and when. The audit viewer CSV export is the first tool used to scope a potential breach.
- CloudWatch Logs retain application logs for 90 days (configurable). Log groups are encrypted via KMS.
- RDS automated snapshots are retained for 35 days. A manual snapshot can be created at incident discovery to preserve state.
- The nightly S3 audit export provides a tamper-evident record that survives even a database compromise.

## Consequences

**Positive:**
- The VPC layout, KMS hierarchy, and audit log design satisfy the HIPAA Security Rule's technical safeguard requirements (§164.312) with well-understood AWS primitives.
- Append-only enforcement at the database trigger layer means audit log integrity does not depend on application code correctness.
- S3 Object Lock compliance mode provides a legally defensible 6-year retention record that cannot be deleted by any principal.
- `.phi.ts` naming and `logger.safe()` enforcement make PHI leakage surface area visible and lintable.

**Negative / Risks:**
- Object Lock compliance mode is irreversible for locked objects. If an incorrect record is written to the audit export bucket, it cannot be deleted for 6 years. Mitigation: the nightly export job is append-only and idempotent. Re-running it for a day creates a new object rather than overwriting.
- Automatic KMS key rotation does not rotate the CMK ARN. If a CMK is compromised (not just the backing key), rotation of the CMK itself requires re-encrypting all data keys. This is a break-glass procedure and is documented in `docs/runbooks/incident-response.md`.
- `logger.safe()` relies on a static list of known PHI field names. Novel field names introduced without updating the scrubber could leak PHI to logs. Mitigation: the ESLint rule flags direct logger calls in `.phi.ts` files; code review must verify that new PHI fields are added to the scrubber list.
